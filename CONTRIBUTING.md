# Contributing

onepact is built one small, real increment at a time — see
[ROADMAP.md](ROADMAP.md) for the running build log and what's next, and
[CHANGELOG.md](CHANGELOG.md) for what shipped when. This file covers the
practical side: getting a dev environment running, and what to check
before you open a change.

## Dev setup

```bash
git clone https://github.com/prajwal2308/onepact.git
cd onepact
pip install -e . pytest pytest-cov ruff mypy
```

That's the whole dependency list — onepact itself has zero runtime
dependencies (see "Why no dependencies?" below), so `pip install -e .`
is instant, and `pytest`/`pytest-cov`/`ruff`/`mypy` are only needed for
development.

## Before opening a change

Run all three, from the repo root:

```bash
pytest -q
ruff check src tests
mypy
```

All three need to pass. There's no separate "format" step — `ruff
check` covers linting (including import order and a handful of
`pyupgrade`-style modernizations; see `[tool.ruff.lint]` in
`pyproject.toml` for the exact rule selection).

CI also runs the suite against Python 3.10 through 3.13 and checks
coverage with:

```bash
pytest -q --cov=onepact --cov-report=term-missing --cov-fail-under=90
```

That's not required locally before every change, but if you're adding
a new code path, give it a look — new code without any test exercising
it is the main way coverage actually drops.

If you're adding or changing behavior, add tests for it in the matching
`tests/test_*.py` file rather than a new file, unless you're introducing
a genuinely new module. If you're fixing a bug, add a test that fails
without the fix.

## Project structure

```
src/onepact/
  cli.py             argparse setup, every command's implementation, main()
  storage.py         Task/Entry/Habit models + their JSON-backed stores
  sqlite_storage.py  SqliteTaskStore -- same interface as the JSON TaskStore
  config.py          ~/.onepact/config.toml read/write, including its
                     minimal hand-rolled TOML parser (see "Why no
                     dependencies?" for why it's not `tomllib`)
  color.py           terminal color autodetection and ANSI formatting
  ui.py              onepact ui's curses dashboard, split so most of it
                     is unit-testable without a real terminal: panel
                     content and line colors (task_lines/habit_lines/
                     journal_lines, task_line_color/habit_line_color)
                     are plain data in, plain strings/color names out;
                     DashboardState/handle_key() track focus and
                     selection as plain indices, with no curses calls
                     beyond key-code constants; toggle_selected_task()/
                     check_in_selected_habit() write real store changes
                     through, reusing storage.complete_task()/
                     check_in_habit() rather than duplicating cmd_done's/
                     cmd_habit_check's logic. Only the actual
                     screen-drawing (_render, _draw_panel,
                     _init_color_pairs) calls curses functions that need
                     a real terminal to run for real -- a fake window
                     object stands in for one in most tests; verified by
                     hand in tmux where that's not enough (color
                     rendering, actual terminal resizing)

tests/
  test_cli.py            every CLI command, end to end
  test_storage.py        Task/Entry/Habit models and their JSON stores
  test_sqlite_storage.py SqliteTaskStore, including equivalence checks
                          against the JSON TaskStore for the same inputs
  test_config.py          config.toml parsing and writing
  test_color.py           color autodetection and NO_COLOR handling
  test_ui.py              ui.py's panel-building/coloring functions,
                          DashboardState/handle_key, and the render
                          loop's focus/selection/activate/too-small
                          handling via a fake curses window (no real
                          terminal needed for any of that)
```

[SCHEMA.md](SCHEMA.md) documents the SQLite schema in more depth than
fits here if you're touching `sqlite_storage.py`.

## Why no dependencies?

onepact intentionally depends on nothing beyond the Python standard
library, including in its tests. A few things fall out of that:

- `requires-python = ">=3.10"` in `pyproject.toml` is a hard floor:
  `tomllib` (the standard library's TOML parser) only arrived in 3.11,
  so `config.py` has its own minimal parser for the flat subset of TOML
  the config file actually needs (`key = "value"` pairs, comments, no
  tables or arrays) rather than dropping 3.10 support or adding a
  dependency for it.
- Shell completion (`onepact completion`) is generated by hand-walking
  argparse's own parser tree instead of adopting a completion library.
- Storage is plain JSON files plus a hand-written SQLite schema, not an
  ORM.

If a change you're considering would pull in a dependency, raise it as
a question in the PR description rather than assuming it's fine — the
answer might be "write the ~20 lines by hand instead," as it has been
for TOML parsing and shell completion so far.

## Roadmap-driven development

[ROADMAP.md](ROADMAP.md) is the single source of truth for what's next.
Its own working rule (worth reading there in full) is: do the first
unchecked item, one at a time, don't skip ahead, keep `pytest -q` green
after every change, and check the item off plus add a dated
[CHANGELOG.md](CHANGELOG.md) entry in the same commit that implements
it. If you're picking up a roadmap item, that's the rule to follow; if
you're fixing something not on the roadmap (a real bug, a test gap), a
focused PR with its own CHANGELOG entry is fine without needing a
roadmap item first.
