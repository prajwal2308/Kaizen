# Changelog

All notable changes to this project are documented here.
Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Changed
- Project renamed from `kaizen` to `onepact`: package, CLI command (`kaizen` → `onepact`), and default data directory (`~/.kaizen` → `~/.onepact`). No behavior change.

### Added
- `kaizen edit <id> <new-title>` command to rename an existing task, with tests.
- `--priority {low,med,high}` on `kaizen add` (default `med`); `list` shows each task's priority and sorts high-priority tasks first.
- `--due YYYY-MM-DD` on `kaizen add`; `list` shows each task's due date and flags past-due, unfinished tasks as `OVERDUE`.
- `--tag <name>` (repeatable) on `kaizen add`; `list` shows each task's tags and `list --tag <name>` filters to tasks carrying that tag.
- `kaizen show <id>` — full detail view of a single task (status, priority, due date with overdue flag, tags, created/completed timestamps).
- `Entry` model and JSON-backed `JournalStore` (load/save/next_id) in `src/onepact/storage.py`, storing journal entries in their own `journal.json`, separate from tasks. First step of Phase 2 (Journaling); no CLI command yet.
- `onepact journal "free text entry"` command that appends a new entry to the journal.
- `onepact journal` with no text argument now opens `$EDITOR` (falling back to `$VISUAL`, then `vi`) for a longer entry; empty entries are discarded rather than saved.
- `onepact journal list` — shows journal entries most recent first (one line each, first line only for multi-line entries), with `--limit N` to cap how many are shown. `journal` is now a command group internally (`add` runs implicitly when the first word after `journal` isn't a known subcommand, so `onepact journal "text"` keeps working unchanged).
- `onepact journal show <id>` — full detail view of a single journal entry (id, timestamp, complete body).
- `--task <id>` on `onepact journal` links a new entry to an existing task; rejects unknown task ids without saving the entry. `journal list` and `journal show` display the linked task when present.
- `onepact journal search <text>` — case-insensitive substring search across journal entry bodies, most recent match first.
- `onepact journal rm <id>` — removes a journal entry after an interactive confirmation prompt (shows the entry's id and first line); `--yes`/`-y` skips the prompt. Declining, or hitting EOF on the prompt, aborts without deleting. This completes Phase 2 (Journaling).
- `onepact find <text>` — case-insensitive substring search across task titles, sorted like `list`; hides completed tasks unless `--all` is passed. Starts Phase 3 (Search, filtering, recurrence). Task line formatting was factored out into a shared `_format_task_line` helper used by both `list` and `find`.
- `list --sort {priority,due,created}` — `priority` (default) keeps the existing high-first ordering, `due` shows the soonest due date first with undated tasks sorted last, and `created` shows the oldest task first.
- `list --overdue` — shorthand filter that shows only past-due, unfinished tasks (the same ones `list` flags `OVERDUE`); combines with `--tag`.
- `--repeat {daily,weekly}` on `add` marks a task as recurring, shown as `[repeat: daily]`/`[repeat: weekly]` in `list`/`find` and as a `Repeat:` line in `show`. This is just the marker for now; auto-creating the next occurrence on completion is a separate, later roadmap item.
- Completing a recurring task now auto-creates its next occurrence: `done` on a task with `repeat` set creates a new task with the same title, priority, tags, and repeat setting, due one day (`daily`) or one week (`weekly`) from the completion date. Non-recurring tasks are unaffected.
- `list --priority <p>` filters to tasks with that priority; combines with `--tag` and `--overdue` since all three are just applied as sequential filters.
- Config file support: `~/.onepact/config.toml` sets defaults, starting with `priority` (used by `add` when `--priority` is omitted; an explicit flag still wins). New `src/onepact/config.py` includes a minimal flat-TOML parser (`key = "value"` pairs, comments, no tables/arrays) rather than adding a dependency or dropping Python 3.10 support, since stdlib `tomllib` needs 3.11+. An invalid `priority` value in the file falls back to `med` rather than erroring.
- `onepact config show` / `onepact config set <key> <value>` — view the current configuration or write a value to `config.toml` from the CLI instead of editing the file by hand. `set` rejects unknown keys and, for `priority`, values outside `low`/`med`/`high`, writing nothing on an invalid call; existing keys in the file are preserved when setting a different one.
- Colorized terminal output: `list`, `find`, `show`, `journal list`, and `journal search` colorize priority, `OVERDUE`, tags, `repeat`, and linked-task markers when stdout is a real terminal. New `src/onepact/color.py` (`should_color()`, `colorize()`) autodetects this — off when piped/redirected, and off on a real terminal too when `NO_COLOR` is set (presence disables it regardless of value, per no-color.org). No `--color`/`--no-color` flag; it's automatic.
- `onepact migrate json-to-sqlite` — copies every task from the JSON store into `~/.onepact/onepact.db` via `SqliteTaskStore`. A copy, not a move: `tasks.json` is untouched, and the command refuses to run (exit 1, nothing written) if the SQLite store already has tasks, so it can't silently double up or clobber data on a second run. Not a switch of the default backend — that's item 34.
- SQLite is now the default storage backend for tasks. A new `backend` config key (`sqlite`, default, or `json`) controls it, read via a new `_get_task_store()` in `src/onepact/cli.py` that every task command now goes through instead of hardcoding `TaskStore()`. The first time the sqlite backend is used and `onepact.db` doesn't exist yet, any tasks already in `tasks.json` are copied over automatically (same copy-not-move semantics as `migrate`), so switching the default can't silently strand existing data — after that first copy, the two stores are independent and further changes to one aren't reflected in the other. `onepact config set backend json` switches back to the JSON store at any point (and `onepact migrate json-to-sqlite` still works exactly as before, always reading from and writing to the JSON/SQLite stores by name regardless of which backend is active). `journal --task <id>`'s existence check now goes through the same active-backend lookup instead of always checking the JSON store.
- `onepact export --format {json,csv}` — dumps every task from whichever backend is active (JSON or SQLite) to stdout, or to a file with `--output`/`-o`. `json` writes the same array-of-objects shape as `tasks.json` (so it's a full-fidelity round trip); `csv` writes a header row plus one row per task with `tags` semicolon-joined (commas inside a CSV field would collide with the delimiter) and `done` as `true`/`false`. Lays groundwork for `import` (item 36).
- `onepact import <file>` — reads tasks from a JSON or CSV file (format inferred from the extension, overridable with `--format`) and appends them to whichever backend is active, assigning each a fresh id via the store's own `next_id()` so importing never collides with or overwrites existing tasks. Every other field (title, priority, due, tags, repeat, done, done\_at, and for JSON, created\_at too) is carried over as-is, so exporting and then importing round-trips a task list. Errors out (exit 1, nothing written) on a missing file, an unrecognized extension with no `--format` override, or a file that doesn't parse as the given format.
- Automatic backups before destructive operations: `rm` and `migrate json-to-sqlite` now copy the file they're about to overwrite into a timestamped `backups/` directory (alongside `tasks.json`/`onepact.db`, so under the active backend's own data directory) before writing, via a new `_backup_file()` in `src/onepact/cli.py`. It's a no-op when the file doesn't exist yet — there's nothing to protect on a first `rm` or first `migrate` — and it never touches the file being backed up, just copies it, so a botched removal or migration always has a copy to recover from. Both commands print where the backup landed.
- `onepact undo` — reverts the last `rm` or `migrate`, restoring the file each one backed up right before overwriting it. A single-level log (`~/.onepact/.undo.json`), written by `_record_undo()` and overwritten on every reversible destructive action, points at exactly one target/backup pair; `undo` restores from it and then deletes both the log entry and the backup file, so running `undo` twice in a row (with nothing destructive in between) reports "Nothing to undo" the second time rather than reaching further back into older backups still sitting on disk. Also reports "Nothing to undo" on a first-ever `migrate` (nothing was backed up, since there was nothing to protect yet) or if the logged backup file has since gone missing.
- `Habit` model (name, frequency, streak, created\_at, last\_checked) and JSON-backed `HabitStore` (load/save) in `src/onepact/storage.py`, storing habits in their own `habits.json`, separate from tasks and journal entries. Habits are identified by name rather than an int id, since `habit add`/`check` both take a name per the roadmap, so there's no `next_id`. `last_checked` is included now even though the streak-increment/reset logic is a later item, the same way `Task.repeat` was added as a marker before auto-creating occurrences was implemented. First step of Phase 5 (Habits & daily review); no CLI command yet.
- `onepact habit add <name> --daily|--weekly` — creates a new habit with that name and frequency (one of the two flags is required; they're mutually exclusive). Rejects a duplicate name (exit 1, nothing written) rather than silently creating a second habit with the same name, since `name` is a habit's only identifier. `habit` is a new command group internally, the same shape as `journal` and `config`.
- `onepact habit check <name>` — marks today's occurrence of a habit done: increments `streak` by one and sets `last_checked` to today, unless `last_checked` is already today, in which case it's a no-op (streak doesn't double-count a second check-in on the same day). This is deliberately the naive version -- it doesn't yet know how many days are "too many" to still count as on-streak for a given `frequency`; that's streak-breaking logic, a later item (45).
- `onepact habit list` — shows every habit's name, frequency, and current streak, one line each, flagging any habit whose `last_checked` is today as `(checked in today)`. `"No habits."` when there aren't any, matching `list`/`journal list`'s empty-store message style. Colorizes `streak: N` and the checked-in flag when stdout is a real terminal, same autodetection as every other colorized command.
- `habit check` now actually breaks a streak on a missed check-in instead of always incrementing regardless of gap (the naive placeholder from item 43): a `daily` habit's streak continues if the gap since `last_checked` is at most 1 day and resets to 1 past that; a `weekly` habit's grace period is 7 days. Checking in resets to a fresh streak of 1 rather than 0, since the check-in itself counts. A new `_today()` in `src/onepact/cli.py` wraps the "what day is it" lookup `habit check`/`habit list` both now use, so tests can monkeypatch it to a fixed date instead of depending on the real clock.
- `onepact review` — a single consolidated view combining three things otherwise spread across `list --overdue`, `habit list`, and `journal show`: overdue, unfinished tasks (sorted the same way `list`/`find` already do), every habit with its current streak and whether it's been checked in today, and the single most recent journal entry. Each section prints its own "nothing here" message (`"No overdue tasks."`, `"No habits."`, `"No journal entries."`) rather than hiding empty sections, so the view's shape is always the same regardless of how much data exists yet. Reads straight from the task/habit/journal stores itself rather than taking one store from `main()`'s dispatch, since no single `store_type` covers all three.
- `onepact review --since yesterday` broadens the journal section from just the single most recent entry to every entry from yesterday or today (most recent first), for catching up after being away a day -- the overdue-tasks and habits sections are unaffected, since "overdue" and "today's streak" are already inherently catch-up-shaped. `--since` only accepts `yesterday` for now, matching the roadmap item as written rather than building out a general date-range parser nothing asked for.
- `onepact stats` — three numbers at a glance: tasks completed in the last 7 days (rolling, not calendar-week, to match `review --since yesterday`'s existing rolling-window style and avoid picking a locale-dependent week-start day), every habit's current streak, and journal entries written in the last 7 days as a rough cadence signal.

### Tests
- Filled gaps in journal command coverage: the explicit `journal add` keyword, an editor-sourced entry linked to a task via `--task`, `journal search` against an empty store, and direct tests of `_read_entry_from_editor` (`$EDITOR`/`$VISUAL` precedence and temp-file cleanup) using a real fake-editor script rather than mocking it away.
- New `tests/test_config.py` covering `load_config`: missing file, quoted/unquoted values, comments, invalid-priority fallback, and unknown keys. Extended with `set_config_value` tests: file creation, overwriting, preserving other keys, and exact written format.
- New `tests/test_color.py` covering `should_color()` (tty/non-tty, `NO_COLOR` set/unset/empty, a stream with no `isatty`) and `colorize()` (single/combined styles, disabled, empty text). CLI tests force color on via a monkeypatched `should_color` to check exact ANSI sequences in `list`/`find`/`show`/`journal list` output, plus one confirming no escape codes appear by default under pytest's non-tty capture.
- Audited Phase 3's sorting/filtering/recurrence/config coverage and filled the real gaps: `--tag`+`--priority`+`--overdue` all combined at once, `--sort` applied after `--overdue` filtering, `--sort due` when every task is undated (falls back to id order), that completing a recurring task marks the *original* done while keeping its `repeat`, that recurrence chains correctly across repeated completions (not just once), and `config show`/`config set` handling an unrecognized key already present in the file. This completes Phase 3 (Search, filtering, recurrence).
- New `tests/test_sqlite_storage.py` mirroring `test_storage.py`'s `TaskStore` tests for `SqliteTaskStore` (round trip, `next_id`, empty store, no file created on a bare `load()`), plus SQLite-specific cases (tag order preserved via `task_tags.rowid`, shared tag names not duplicated across tasks, `save()` fully overwriting prior contents, `load()` ordering by id) and a direct equivalence test that runs the identical add/done/rm sequence against both `TaskStore` and `SqliteTaskStore` and asserts the resulting task lists match field-for-field.
- CLI tests for `migrate json-to-sqlite`: copying tasks (title/priority/tags/repeat preserved, JSON store left untouched), an empty JSON store, refusing to overwrite existing SQLite data, and the invalid-direction error. Extended the isolated-store test fixture to bind `SqliteTaskStore` to `tmp_path` the same way the other stores already are.
- Backend-switch coverage: fresh installs default to sqlite, `config set backend json`/`sqlite` actually changes which store `add`/`list` use, auto-migration of existing `tasks.json` tasks the first time sqlite is used (and that it does *not* re-run once `onepact.db` already exists), `migrate json-to-sqlite` ignoring the `backend` config and always using the JSON store, `journal --task` validating against whichever backend is active, and invalid `backend` values being rejected by `config set`. The autouse test fixture now forces `backend="json"` by default so all the existing store-reading tests keep exercising the JSON store unchanged; the new backend tests explicitly opt back into the real default. New `test_config.py` cases cover `load_config`'s `backend` default, file override, and invalid-value fallback.
- `export` coverage: JSON output parses back to the expected task fields (including tags, done/done_at, due, repeat) for both a populated and an empty store, CSV output has the expected header and rows with tags joined by `;`, both formats written to `--output`/`-o` land correctly on disk with the right confirmation message, missing/invalid `--format` errors out, and export reads from whichever backend (JSON or sqlite) is currently active.
- `import` coverage: a full `export` → clear the store → `import` round trip for both JSON and CSV (every field matches except id), format inferred from `.json`/`.csv` extensions and overridden via `--format`, an unrecognized extension without `--format` erroring out, a missing file, malformed JSON, importing into an already-populated store appending with freshly assigned ids rather than clashing, missing optional JSON fields falling back to the same defaults `Task.from_dict` already uses, and importing writing into whichever backend (JSON or sqlite) is currently active.
- Backup coverage: `rm` backs up the pre-removal file with matching content and reports where, an unknown id creates no backup (nothing was written), and the same backs-up-from-whichever-backend-is-active check as other destructive commands; `migrate` backs up an existing (even empty) sqlite file before overwriting it, and creates no backup on a genuinely first-ever migrate (there's nothing to protect yet).
- `undo` coverage: reverting a `rm` and a `migrate` each restores the exact pre-write content, the consumed backup file is deleted afterward, calling `undo` twice in a row errors the second time instead of reaching an older backup, undoing after two `rm`s in a row only reverts the most recent one and leaves the older one unreachable, `undo` with no prior destructive action (or after a first-ever `migrate`, which has nothing to back up) errors with "Nothing to undo", and a logged backup file that's gone missing is handled without a crash.
- Audited data-integrity coverage for `migrate` and `export`/`import` and filled the real gaps: the existing `migrate` tests only checked a handful of fields on one or two tasks, so a new field-by-field round-trip test covers five tasks spanning every combination that matters (no due/tags at low priority, several tags at high priority, a due date with a weekly repeat, and a daily-repeat task completed mid-test so its auto-created next occurrence is covered too) and asserts every field -- including `id` and `created_at`, which nothing previously checked survived a migration -- matches exactly between the JSON source and the migrated SQLite copy. The existing export/import round-trip tests only ran against the JSON backend (forced on by the test fixture); a new test forces the real sqlite-default backend instead and confirms the same field-for-field round trip holds there too.
- New `Habit`/`HabitStore` tests in `tests/test_storage.py`, mirroring the existing `Entry`/`JournalStore` coverage: `streak`, `last_checked`, and `created_at` defaults both on direct construction and via `from_dict` on legacy data missing those keys, a save/load round trip across multiple habits, and that `HabitStore` is independent of `TaskStore`/`JournalStore` in the same data directory.
- CLI tests for `habit add`: daily and weekly habits store the right fields with `streak`/`last_checked` at their defaults, a duplicate name errors out without touching the existing habit, `--daily`/`--weekly` is required and mutually exclusive, and `habit add` doesn't disturb `TaskStore`/`JournalStore` in the same data directory. Extended the isolated-store test fixture to bind `HabitStore` to `tmp_path` the same way the other stores already are.
- CLI tests for `habit check`: the first check-in moves `streak` from 0 to 1 and sets `last_checked` to today, a second check-in the same real day doesn't double-count, a habit whose `last_checked` is set (via direct `HabitStore` manipulation) to a past date increments again and advances `last_checked` to today, an unknown habit name errors out, and checking one habit leaves every other habit's `streak`/`last_checked` untouched.
- CLI tests for `habit list`: the empty-store message, name/frequency/streak shown for multiple habits, only a habit actually checked in today being flagged `(checked in today)` (not an unrelated habit), and exact ANSI codes for the streak and checked-in-today colorizing when forced on.
- Streak-breaking tests, all driven by monkeypatching `onepact.cli._today` to a fixed date rather than depending on real wall-clock time (per the roadmap item's own "tested with fixed clock" requirement): a `daily` habit continues its streak exactly at the 1-day grace boundary and resets just past it; a `weekly` habit does the same at the 7-day boundary. Replaced the old `test_habit_check_on_a_later_day_increments_again`, which asserted the pre-item-45 naive always-increment behavior for a large gap -- that assumption is no longer correct now that a large gap resets the streak instead.
- `review` coverage: every section's empty-state message when there's no data at all, only overdue *and unfinished* tasks appear (not a future-due task, not an overdue task that's already done), overdue tasks are sorted high-priority-first the same way `list` is, every habit shows up with its current streak and only the actually-checked-in-today one is flagged, and only the single most recent journal entry is shown, not older ones.
- `review --since yesterday` coverage, driven by a fixed, monkeypatched `_today()` plus directly-set `created_at` values for precise control: entries from both yesterday and today appear while an older one doesn't, matching entries show most-recent-first, the empty-state message, and an invalid `--since` value erroring out via argparse's own `choices` validation.
- `stats` coverage, also driven by a fixed `_today()` plus directly-set `done_at`/`created_at` values: the empty-state numbers are all zero, a task completed 6 days ago (the oldest day still inside the 7-day window) counts while one completed 7 days ago doesn't, every habit's streak is shown by name, and the same within/outside-the-window boundary check for journal entries.
- Audited habit/review/stats coverage and filled the real gaps: `Habit.from_dict` defaulting `frequency` to `"daily"` on legacy data missing that key was the one field without a matching test (every other defaultable field already had one); `review` never had a case confirming a task with no due date at all is correctly excluded from the overdue section, nor a forced-color test like every other list-style command already has (`list`, `find`, `show`, `journal list`, `habit list`); and neither `review` (its overdue-tasks section) nor `stats` (its completed-this-week count) had been checked against the real sqlite-default backend specifically, only against the JSON store the test fixture forces by default.

### Docs
- README: new "Journaling" section documenting `journal` (append, `$EDITOR`, `--task` linking), `journal list` (`--limit`), `journal show`, `journal search`, and `journal rm` (confirmation prompt, `--yes`), plus the `~/.onepact/journal.json` storage location. Every example command was run against a clean data directory to confirm its shown output.
- README Usage section now documents `find`, `list --sort`, `list --overdue`, `list --priority` (and combining filters), and `--repeat` (including completing a recurring task) alongside `list`.
- README "Configuration" section documents `~/.onepact/config.toml`, the `priority` key, and now `config show`/`config set` as the way to view and change it from the CLI.
- New README "Color" section documenting autodetection and `NO_COLOR`.
- New `SCHEMA.md`: the SQLite schema `SqliteTaskStore` (item 32) will implement, designed as a direct equivalent of the current JSON model — `tasks`, a normalized `tags`/`task_tags` join (`Task.tags` isn't a native SQLite type), and `journal_entries`, with a JSON-field-to-column mapping table, `CHECK` constraints on `priority`/`repeat`/`done`, indexes on the columns `list --overdue`/`--priority`/`--tag` already filter by, and notes on keeping id assignment app-controlled (not SQLite `AUTOINCREMENT`) so migration can insert existing ids and both backends stay interchangeable. Starts Phase 4 (Storage evolution & data safety). Nothing is wired up yet — every `CREATE TABLE`, its `CHECK` constraints, defaults, and `ON DELETE` behavior were executed and verified against Python's stdlib `sqlite3`, not just written down.
- New `src/onepact/sqlite_storage.py`: `SqliteTaskStore` implements SCHEMA.md's `tasks`/`tags`/`task_tags` tables behind the exact same `load()`/`save()`/`next_id()` interface as `TaskStore` (duck-typed, not a subclass, since the two backends' internals have nothing in common) -- a drop-in replacement once item 34 switches the default. `save()` replaces the whole `tasks`/`task_tags` content each call, matching the JSON store's whole-file-overwrite semantics; tag names are deduplicated across tasks via `tags.name UNIQUE`, and tag order is preserved per task through `task_tags.rowid`. Not wired into the CLI yet -- `TaskStore` (JSON) is still what every command uses.
- New README "Migrating to SQLite" section documenting `migrate json-to-sqlite`, linking to SCHEMA.md, and being explicit that this is a preview -- the CLI doesn't read from SQLite yet.
- README "Backups" section renamed to "Data & backups" and given a table listing every file `onepact` stores under `~/.onepact/` (`onepact.db`, `tasks.json`, `journal.json`, `config.toml`, `backups/`, `.undo.json`), which was previously only documented piecemeal across other sections (or, for `.undo.json`, not documented at all). Adds a closing note on backup strategy: the automatic `rm`/`migrate` backups and `undo` only protect against a single bad command since they live inside `~/.onepact/` itself, so real disaster recovery -- losing the whole directory -- means periodically `export`ing tasks somewhere else entirely. This completes Phase 4 (Storage evolution & data safety).
- New README "Daily habits & review workflow" section. "Habits", "Daily review", and "Stats" already each documented their own commands and flags in isolation; this one ties them together into an actual day-in-the-life example -- add habits once, run `review` each morning, check habits off and journal through the day, use `review --since yesterday` to catch up after time away, and check in on `stats` occasionally -- rather than leaving it to the reader to piece the workflow together from three separate reference sections. This completes Phase 5 (Habits & daily review).
